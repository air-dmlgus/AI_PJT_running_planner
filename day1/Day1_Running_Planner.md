# 러닝 코스 추천 AI Agent · 1일차 기획서

## 1. 서비스 범위

사용자가 지역, 달릴 날짜·시각, 거리, 날씨·대기질 조건을 말하면 공개 코스 데이터와 예보를 비교해 러닝 계획을 제안한다. 조건을 충족하는 코스가 없으면 사용자가 허용한 범위에서 대체 시각이나 지역을 탐색한다. 추천 결과를 저장하고 나중에 수정하거나 삭제할 수 있다.

추천 목표 거리는 짧은 러닝부터 **하프마라톤 21.0975km**까지다. 첫 시연 지역은 두루누비에서 짧은 거리와 하프 거리 후보의 거리·GPX를 함께 확인할 수 있는 곳으로 우선 검토한다. 기존 코스의 전체 구간을 추천하며, 첫 버전에서 지원하는 날씨 기준은 코스 출발 지점의 출발 시간대다. 대기질은 날짜·권역 단위의 예보 등급으로 보여준다. 둘레길 데이터의 걷기 소요시간은 러닝 예상 시간 계산에 사용하지 않는다.

### 외부 데이터와 이용 조건

| 제공기관·API | 쓸 값 | 개발계정 한도 참고 | 이용 조건 |
|---|---|---:|---|
| [한국관광공사 두루누비](https://www.data.go.kr/data/15101974/openapi.do) | `courseList`의 코스 ID, 이름, 시군, 거리, GPX 경로 | 1,000건 | 무료, 포털 표기상 이용허락범위 제한 없음 |
| [기상청 단기예보](https://www.data.go.kr/data/15084084/openapi.do) | `getVilageFcst`의 예보 일시, 강수형태(PTY), 강수확률(POP), 기온(TMP) | 10,000건 | 무료, 출처 표시 및 제3자 권리 표기 확인 |
| [한국환경공단 에어코리아](https://www.data.go.kr/data/15073861/openapi.do) | 예보통보의 PM10·PM2.5 등급, 발표 일시, 적용 날짜 | 500건 | 무료, 출처 표시·변경 금지 표기 및 제3자 권리 확인 |

한도 값은 기획 참고치다. 실제 계정에 표시되는 상한과 단위를 확인해 검증표에 기록한다. 외부 출처와 예보의 공간·시간 단위를 추천 근거에 함께 표기한다. 서비스는 코스와 예보 정보를 제공하며, 예보는 실제 상황과 달라질 수 있다.

## 2. 대표 사용자 요청

아래 요청의 지역명은 확인된 시연 지역으로 치환한다. 모든 시각은 한국 시간이다.

| 요청 | 기준·선호·제약 | Tool 순서와 기대 결과 | Tool 없이 확인할 수 없는 값 |
|---|---|---|---|
| “오늘 저녁 7시에 이 지역에서 10km 정도. 강수 예보 없고 초미세먼지 보통 이하였으면 좋겠어.” | 기준 오늘 19시 / 선호 이 지역 / 거리 9~11km, 무강수, PM2.5 보통 이하 | 코스 → 출발지 날씨·권역 대기질 → 조건 충족 후보 제시 | 코스의 실제 거리, 19시 강수형태, 당일 권역 대기질 등급 |
| “내일 오전 7시에 이 지역에서 하프 정도 뛰고 싶어. 6분/km 페이스고 비 예보 없는 곳으로.” | 기준 내일 07시 / 선호 이 지역 / 20~22km, 출발 시각 무강수, 6분/km | 코스 → 단기예보 → 실제 코스 거리로 소요 시간·종료 시각 계산. 후보가 없으면 거리 차이와 대안을 안내 | 하프 거리대 후보·GPX와 출발지 강수형태 |
| “내일 오후 6시에 이 지역에서 5km. 비 예보가 있으면 저녁 8시까지 미뤄도 돼.” | 기준 내일 18시 / 선호 이 지역 / 5km, 무강수, 19·20시 대체 허용 | 코스 → 단기예보 → 18시 강수 예보가 있으면 확보한 예보로 19·20시 재평가 | 후보 거리와 시간대별 강수형태 |
| “토요일 오전 8시에 이 지역에서 8~12km. 초미세먼지는 보통 이하. 근처 다른 지역도 가능해.” | 기준 토요일 08시 / 선호 이 지역 / 8~12km, PM2.5 보통 이하, 인접 지역 허용 | 코스 → 대기질 → 충족 후보가 없으면 사전 정의한 인접 지역 후보 탐색 | 후보 거리와 권역별 대기질 등급 |

| “같은 조건에서 8시로 바꿔줘.” | 이전 요청의 조건 + 출발 시각 수정 | 오전·오후가 문맥에서 명확하면 갱신 후 재평가. 모호하면 질문 | 바뀐 시간대의 실제 강수 예보 |
| “이 서비스 어떻게 써?” | 사용법 질문 | Tool 없이 답변 | 해당 없음 |

## 3. Tool 정의서

| Tool | 선택하는 상황 | 입력 | 출력 `data` |
|---|---|---|---|
| `search_courses` | 특정 지역의 러닝 후보와 실제 코스 속성이 필요할 때 | `area: str`, `min_km?: number`, `max_km?: number` | `courses[]`의 `id, name, area, distance_km, gpx_url, start_lat, start_lon, air_region`. 입력 범위로 필터링하며 거리 필드 단위와 지역 매핑을 확인한다. |
| `get_weather` | 후보 출발 지점·시간대의 강수 예보가 필요할 때 | `lat, lon: number`, `start_at: ISO datetime` | `grid, issued_at, hourly[]`의 `forecast_at, precipitation_type, precipitation_probability_pct, temperature_c`. 같은 응답에 들어 있는 인접 시각은 재사용한다. |
| `get_air_quality` | 코스 권역의 미세먼지·초미세먼지 예보 등급이 필요할 때 | `region: str`, `target_date: ISO date`, `pollutants: list[PM10 또는 PM25]` | `region, target_date, grades, issued_at`. 통보일 검색 결과에서 예보 적용일과 권역이 일치하는 최신 항목을 고른다. |

공통 응답은 `{ok: true, data: …}` 또는 `{ok: false, error: {code, message}}`다. 실패 코드는 `INVALID_INPUT`, `NO_RESULT`, `MISSING_DATA`, `OUT_OF_FORECAST_RANGE`, `API_KEY_MISSING`, `UPSTREAM_ERROR`를 사용한다. 부분 결측은 해당 값을 비워 두고 다른 후보를 계속 평가한다. 필수 Tool 세 개를 이름·설명·입력 스키마와 함께 등록하고, 이후 Tool도 같은 형식으로 추가한다. 계획 CRUD, 지역 매핑, 시간·거리 계산, 캐시는 서버와 Agent의 실행 흐름에서 처리한다.

## 4. Agent 설계

| 단계 | 받는 상태 | 넘기는 상태 |
|---|---|---|
| 분석 | 사용자 메시지, 직전 세션 상태 | 의도, 기준·선호·제약, 빠진 값, 허용된 대안 범위 |
| 계획 | 구조화된 조건 | Tool 호출 순서, 앞 Tool의 출력에서 가져올 인자 |
| 실행 | 작업 목록, 실행 중 캐시 | 후보, 예보, 실패 목록, 소요 시간 |
| 판단 | 후보와 조건, 재계획 횟수 | 후보별 충족·불충족·확인 불가, 근거, 다음 탐색 범위 |
| 응답 | 판정 결과, 재계획 종료 사유 | 추천 또는 대안, 제외 이유, 근거, 저장 가능한 계획 초안 |

- 거리 범위는 사용자가 지정한 값을 우선한다. “10km 정도”에는 ±10%를 적용한다. “하프”나 “하프 정도”는 목표 21.0975km와 탐색 범위 20~22km로 해석하고, 목표와 가까운 후보부터 실제 코스 거리와 차이를 보여준다. “정확히 하프”는 엄격한 거리 조건으로 처리한다. 공개 데이터의 거리 정밀도가 부족하면 정확 일치 여부를 확인 불가로 표시하고 근접 후보를 별도로 안내한다.
- “비 없게”는 요청 출발 시각이 속한 시간대의 `PTY = 0`을 기준으로 판단하고 `POP`도 함께 표시한다. 예보 범위를 벗어난 시각이나 결측 값은 확인 불가로 처리한다.
- 대기질은 `좋음 < 보통 < 나쁨 < 매우 나쁨` 순으로 비교한다. 같은 날 같은 권역은 시각을 바꿔도 같은 등급을 재사용한다.
- 종료 시각은 사용자가 입력한 페이스가 있으면 `출발 시각 + 코스 km × 분/km`로 계산한다. 예를 들어 21.0975km를 6분/km로 달리면 약 2시간 6분 35초다. 페이스를 모르면 추천까지 진행하고, 저장 전에 예상 종료 시각이나 페이스를 받는다. 종료 제한과 페이스가 주어지지 않고 마감만 있으면 `남은 분 ÷ 코스 km`로 필요한 최대 페이스(분/km)를 보여준다.
- 모든 제약을 충족하는 후보가 없을 때 허용된 시간 후보부터, 그다음 허용된 지역 후보를 탐색한다. 초기 탐색 이후 재계획은 최대 2회다. 조건을 임의로 완화하지 않고, 키 누락과 입력 부족은 바로 안내한다. 동일 입력의 성공한 Tool 응답을 실행 중에 재사용한다.
- 세션에는 직전의 구조화된 조건과 추천 요약을 보관한다. 후속 요청에서는 바꾸라고 한 값만 갱신한다. 인증 정보, 원본 응답 전체, 이전 예보를 이후 요청의 최신 값처럼 저장하지 않는다.

## 5. 로그·저장·API 설계

메인 Agent는 `stage_started`, `stage_finished`, `tool_called`, `tool_finished`, `decision_made`, `replanned` 이벤트를 발행한다. 이벤트 공통 필드는 `session_id, run_id, seq, event_type, occurred_at, stage, payload`다. Tool 완료 이벤트에 성공 여부, 요약, 오류 코드, 소요 시간을 넣는다. LLM 판단 이벤트에는 선택한 의도·행동과 짧은 판단 근거를 남긴다. 로깅 Agent는 LLM 호출 없이 이벤트를 SQLite에 저장하고, 메인 Agent는 로깅 구독 여부와 관계없이 응답한다.

계획은 `id, course_id, course_name, run_date, start_at, end_at, distance_km, evidence, created_at, updated_at`을 저장한다. 같은 날짜에서 `새 시작 < 기존 종료`이면서 `기존 시작 < 새 종료`이면 겹치는 계획 ID를 반환하고 저장을 계속한다. 종료 후 바로 이어지는 계획은 겹침으로 처리하지 않는다.

| API | 요청 | 응답 |
|---|---|---|
| `POST /chat` | `{session_id?, message}` | `{session_id, run_id, status, answer, recommendation, execution}` |
| `POST /plans` | 사용자 확인을 거친 계획 데이터 | 201, `{plan, conflicts[]}` |
| `GET /plans`, `GET /plans/{id}` | 목록 또는 계획 ID | 200, 목록 또는 계획 상세 |
| `PATCH /plans/{id}` | 변경할 필드 | 200, `{plan, conflicts[]}` |
| `DELETE /plans/{id}` | 계획 ID | 204 |
| `GET /logs`, `GET /logs/{session_id}` | 목록 또는 세션 ID | 200, 목록 또는 순서대로 정렬된 이벤트 |
| `DELETE /logs/{session_id}` | 세션 ID | 204 |

대화 화면은 메시지 입력, 처리 중 표시, 추천·근거, 실행 단계·Tool 이력·재계획, 오류 안내를 보여준다. 계획 관리 화면은 목록·상세·수정·삭제와 일정 겹침 알림을 제공한다. 심화 검토 후보는 F3020(이상 징후 판단)이다. 같은 입력 반복 호출, 상한 초과, 계획 밖 호출을 이벤트로 판별할 수 있다.

## 7. 기획 검증 기록

| 항목 | 확인할 증거 | 상태 |

**정상 요청 설계 검토** · 코스 거리와 GPX 출발점 확인 → 출발 좌표를 날씨 조회에, 코스 권역과 날짜를 대기질 조회에 전달 → 세 조건이 모두 충족되면 추천. 날씨 격자·대기 권역 매핑은 실제 지역을 정한 뒤 대조한다.

**재계획 설계 검토** · 18시 강수 판정 실패 → 허용된 19·20시 예보를 기존 응답으로 재평가 → 둘 다 실패하면 사용자가 허용한 추가 대안이 있는 경우에만 한 번 더 탐색 → 조건 또는 상한에 따라 종료. 결과에 강수 시간대와 제외 사유를 표시한다.

**16시 도메인 판정** · 명세서 기준으로 1일차 16시까지 API 3종을 코드로 호출하고 필요 필드를 확인한다. 통과 시 시연 지역과 구현 범위를 확정한다. 미통과 시 제공 영화 도메인 팩으로 전환한다.

## 검증 스크립트 실행

1. 공공데이터포털에서 API 3종에 각각 활용 신청한다. 발급받은 **Decoding 키**를 사용한다.
2. 같은 폴더의 `env.example`을 `.env`로 복사하고 키를 채운다. GMS 연결은 과정에서 안내한 URL과 모델을 우선한다.
3. Python 3.10 이상에서 `python verify_apis.py`를 실행한다. 외부 API와 LLM 연결 점검 결과를 JSON으로 출력한다. 개별 점검은 `python verify_apis.py course`, `weather`, `air`, `llm` 중 하나를 선택한다.
4. 첫 호출의 기상 격자와 대기 권역은 샘플 값이다. 두루누비 결과에서 검증할 코스를 정한 뒤 GPX 시작점을 열어 격자를 확인하고, `.env`의 격자와 대기 권역을 갱신한 뒤 다시 실행한다. 코스명 일부를 `COURSE_QUERY`에 넣으면 해당 후보만 점검한다.
5. `python verify_apis.py half`로 20~22km 후보의 거리와 GPX 주소를 확인한다. 이 명령은 `COURSE_QUERY`가 비어 있으면 전체 목록에서 찾으며, 목표 거리에 가까운 순으로 최대 3개를 출력한다. 후보를 고른 뒤 GPX 파일을 열어 경로와 출발점을 확인한다.
6. 검증표에 실제 응답의 필드·값·시간대를 옮긴다. 키가 들어 있는 `.env`는 Git에 추가하지 않는다.
